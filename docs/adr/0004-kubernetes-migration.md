# ADR 0004: Migrate from Docker Compose to Kubernetes (k3s)

## Status
Accepted

## Context
The homelab currently runs as one Docker Compose stack per service group (ADR 0003), on a single Arch Linux desktop, fronted by `nginx-proxy-manager` as the sole public listener (ADR 0002's storage layout underneath). This has worked well for a self-contained single-host setup, but three things now push past what it comfortably supports:

1. **Backups.** There is no first-class scheduled backup mechanism for `homelab-conf`/`homelab-data` beyond ad hoc scripting.
2. **Public scale-out.** The plan is to host a growing set of personal applications publicly, with the ability to add external nodes and horizontally scale specific services rather than being permanently pinned to one box.
3. **Shared cluster with yggdrasil.** The `yggdrasil` stack (`containers/yggdrasil/`) already targets a Kubernetes API for its Orchestrator (ADR 003 upstream in that project) and expects an externally-configured k3s cluster + kubeconfig, configured entirely in-app rather than bundled by its compose project. Running a second, homelab-specific cluster alongside the one yggdrasil expects would be redundant.

There is also an explicit goal of building hands-on familiarity with Kubernetes and its ecosystem (Traefik, cert-manager, CronJobs, namespaces, PVCs), which argues for adopting real k8s primitives rather than the minimum shim needed to keep today's containers running.

## Decision
Migrate the homelab from per-stack Docker Compose to a single **k3s** cluster, adopted incrementally (stack by stack, not a flag-day cutover).

- **Distribution:** k3s, not full kubeadm/managed k8s. It is lightweight enough for the current single-node reality, ships Traefik and a local-path-provisioner out of the box, and is multi-node capable — external nodes can be joined later with no re-architecture. It is also the distribution `yggdrasil`'s Orchestrator already expects, so this becomes the one cluster both the homelab stacks and yggdrasil's deployed projects share.
- **Namespaces:** one namespace per stack (`homelab-arr`, `homelab-jellyfin`, `homelab-immich`, ...), plus reserved namespaces for `yggdrasil` and the projects it deploys (`yggdrasil-apps` or similar), so RBAC and NetworkPolicies can be scoped per concern from day one.
- **Storage:** PVCs backed by k3s's local-path-provisioner initially, pointed at the existing `homelab-conf`/`homelab-data` host paths (ADR 0002's split is preserved, just re-expressed as PVs). Multi-node storage (Longhorn/Rook) is deferred until external nodes are actually added.
- **Backups:** namespaced CronJobs (restic or rsync-based) snapshot `homelab-conf`/`homelab-data` PVCs to off-box storage. This is built early, independent of which stacks have migrated yet, since it's low-risk and immediately useful.
- **Ingress:** `nginx-proxy-manager` is retired, not re-hosted. Traefik (bundled with k3s) plus `cert-manager` (Let's Encrypt) handle all routing and TLS, expressed as `Ingress`/`IngressRoute` YAML checked into this repo — no GUI-based proxy-host configuration. NetworkPolicies gate which namespaces may be reached from publicly-exposed Ingress routes.
- **Migration order:** convert one low-blast-radius, non-public stack first as a proof of concept (e.g. `searxng` or `atuin`), then the ingress replacement itself (built in parallel/staging before DNS cutover), then remaining stacks, saving the most fragile (`arr`'s gluetun VPN sidecar, `immich`/`nextcloud` with non-default container users) for last.
- **Workload packaging:** every stack — both this homelab's own services and the growing set of personal projects to come — is defined as a **Helm chart**, not plain YAML or Kustomize. A shared library/umbrella chart holds common templates (Deployment, Service, PVC, Ingress, standard labels/namespace conventions) so each new personal project mostly supplies a `values.yaml` rather than hand-writing manifests from scratch. Third-party infra (kube-prometheus-stack, cert-manager, Loki) is installed via its own upstream Helm chart, same tooling either way. Charts live in a top-level `helm/` directory (`helm/<stack>/`, plus the shared `helm/homelab-common` library chart) — kept separate from `containers/`, which stays exclusively Compose — and env templates (`*.example`) map to a `values.secret.example.yaml` following the same "never commit secrets" rule.
- **Secrets (Sealed Secrets):** each stack's secrets are committed to git as **`SealedSecret`** manifests (`helm/<stack>/templates/sealed-*.yaml`) — encrypted client-side with `kubeseal` against the in-cluster Sealed Secrets controller's public key, decryptable only by that controller. This is what makes secrets ArgoCD-compatible (everything reconciles from git, no imperative-only step left over) without a new external dependency like a vault service. Two things this doesn't solve on its own: (1) losing the controller's private key makes every committed `SealedSecret` permanently undecryptable, and (2) something has to hold the plaintext outside git in the first place. Both are handled by `scripts/k8s-secrets/copy_secrets.sh` / `apply_secrets.sh`, a k8s-native pair mirroring `scripts/env/copy_env.sh` / `apply_env.sh`: `copy_secrets.sh` backs up the controller's signing key(s) plus any not-yet-sealed plaintext Secret to the clipboard as JSON (paste into the same vault as the `*.env` export, e.g. Bitwarden); `apply_secrets.sh` restores both into a rebuilt cluster. Per-stack secrets are converted to `SealedSecret`s as each stack migrates (see `helm/atuin` for the reference pattern); `values.secret.example.yaml` is no longer used once a stack has sealed secrets.
- **GitOps delivery (ArgoCD):** once the shared library chart and the first PoC stack are proven stable via manual `helm upgrade --install`, adopt **ArgoCD** as the ongoing lifecycle mechanism for everything migrated after that point. ArgoCD runs in-cluster, watches this repo's chart paths, and reconciles live cluster state to what's committed — `git push` becomes the deploy step, replacing `up-all-stacks.sh`/`down-all-stacks.sh` for k8s-migrated stacks. It's introduced deliberately *after* the PoC, not alongside it, so chart structure isn't churning underneath a reconciliation loop while still being worked out by hand. `yggdrasil`'s own namespace(s) are left to its own Orchestrator to manage directly rather than folded into ArgoCD's watch scope, unless yggdrasil's deploys also land as commits to a repo ArgoCD can watch.
- **Monitoring:** a dedicated `monitoring` namespace runs the observability stack for the whole cluster, covering logs, container/pod state, and node resource usage:
  - **Metrics:** `kube-prometheus-stack` (Prometheus + Grafana + Alertmanager, via its Helm chart), which bundles `node-exporter` (host resource usage: CPU/mem/disk/network per node) and `kube-state-metrics` (k8s object state: pod/deployment/PVC health, restarts, resource requests vs. limits).
  - **Logs:** Loki + Promtail (or Grafana Alloy), scraping container logs cluster-wide and queryable from the same Grafana instance — replaces manually `docker logs`-ing into each stack.
  - **Container-level detail:** cAdvisor metrics come in via `kube-state-metrics`/`node-exporter` scraping already exposed by kubelet, so no separate cAdvisor deployment is needed.
  - Grafana is exposed through the same Traefik + cert-manager Ingress as everything else (e.g. `grafana.<domain>`), gated behind auth (Grafana's own login, at minimum) since it will show data about every namespace including yggdrasil's.
  - This is built alongside the backup CronJobs, early and independent of stack migration order, since it's what makes every later migration step verifiable (you can watch a stack's resource usage and logs in Grafana the moment it lands, instead of falling back to `kubectl logs`/`describe`).

## Alternatives considered
- **Full kubeadm cluster / managed k8s (EKS-like on-prem via k0s, etc.)** — more "production-grade" but higher operational overhead for a homelab, and no meaningful benefit over k3s at this scale.
- **Stay on Docker Compose, add cron-based backups only** — solves goal #1 cheaply, but does nothing for public horizontal scaling or the explicit learning goal, and leaves yggdrasil's cluster and this homelab's stacks split across two separate control planes.
- **Keep `nginx-proxy-manager` running inside the cluster as the ingress** (Deployment + MetalLB `LoadBalancer` Service, proxying to in-cluster Services) — preserves the familiar GUI for subdomain/cert management. Rejected in favor of native `Ingress`/`cert-manager` YAML: it's more idiomatic k8s, fits the learning goal, and keeps routing config in git (GitOps) rather than in NPM's SQLite state.
- **Big-bang cutover** — rejected; per-stack incremental migration matches the existing per-stack compose isolation (ADR 0003) and lets each stack's risk be assessed independently.
- **Plain YAML manifests or Kustomize per stack** — more transparent and less indirection, and initially preferred for learning the raw objects. Rejected once the scope grew to "many personal projects": with dozens of stacks eventually deployed, Helm's templating (a shared chart + per-stack `values.yaml`) avoids copy-pasting near-identical Deployment/Service/Ingress boilerplate for every new project, at the cost of an extra layer of indirection over raw manifests.

## Consequences
- Every stack eventually gains a Helm chart counterpart under the top-level `helm/<stack>/` directory (kept separate from `containers/`, which stays Compose-only); Compose files are removed for a stack once its chart is verified working, not before.
- `up-all-stacks.sh` / `down-all-stacks.sh` stop being the lifecycle mechanism for migrated stacks; `helm upgrade --install` (directly or via a thin wrapper script, plus a shared library chart repo/path) takes over. During the transition period both mechanisms coexist for different stacks.
- A shared library chart needs to exist before the second stack migrates, or per-stack charts will duplicate boilerplate the library chart was meant to avoid — worth building alongside the first PoC stack, not after.
- After the PoC stack, `helm upgrade --install` is itself superseded by ArgoCD for any stack migrated from then on; `up-all-stacks.sh`/`down-all-stacks.sh` and manual `helm` invocations only remain relevant for stacks still on Compose or mid-PoC.
- The storage convention (`homelab-conf` vs `homelab-data`, ADR 0002) is preserved conceptually but re-expressed as PVs/PVCs rather than bind mounts.
- **k3s's bundled Traefik defaults to a `LoadBalancer` Service.** Its `ServiceLB` (klipper) component installs iptables rules that intercept externally-arriving traffic on host ports 80/443 and redirect it into the cluster, regardless of what Docker already has bound to those ports — this silently hijacked all public `*.smugiwara.com` traffic away from `nginx-proxy-manager` the first time k3s was installed (traffic to `localhost` was unaffected, only externally-sourced connections were redirected, which made it look like an NPM outage rather than a routing conflict). Until the deliberate ingress cutover happens, Traefik's Service must stay patched to `ClusterIP` (`kubectl patch svc traefik -n kube-system -p '{"spec": {"type": "ClusterIP"}}'`) so it only serves in-cluster/test traffic and never competes with NPM for host ports. Re-check this after any k3s upgrade or reinstall — it resets to `LoadBalancer` by default.
- `nginx-proxy-manager`'s stack directory is removed once cutover completes; Traefik + cert-manager configuration becomes its own chart/concern under `helm/`, to be settled when that work starts.
- CLAUDE.md's "no host port publishing for HTTP services" / `edge` network rules apply only to still-Compose stacks; migrated stacks are governed by Ingress + NetworkPolicy instead, and CLAUDE.md will need a follow-up update once the first stack lands to document the new agent rules for k8s manifests.
