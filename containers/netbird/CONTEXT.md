# netbird Stack Context

## Glossary

**netbird-stack** — compose project `netbird-stack` in `containers/netbird/`. Self-hosted NetBird control plane, trimmed down from the version retired in commit `a2b33c6` (2026-08-08).

**netbird-server** — `netbirdio/netbird-server` image. Combines what used to be three separate containers (management, signal, relay) plus STUN into one process, configured by a single `config.yaml`. This is the current upstream architecture (replaces the old `management.json` + separate-container layout) — see `getting-started.sh`'s `render_combined_yaml`.

**dashboard** — `netbirdio/dashboard` UI, for managing peers/ACLs/setup keys. Not required for the VPN data plane to function — safe to `docker compose stop dashboard` between admin sessions and start it again when needed (`docker compose start dashboard`).

**What's gone from the old setup, and why**:
- **Separate signal/relay containers** — folded into `netbird-server` by upstream; nothing to trim here ourselves.
- **Routing peer container** (`netbird-routing` in the old stack) — that existed to advertise LAN routes so *other* devices became reachable through netbird (acting as a gateway/exit node). This deployment's only goal is SSH access to this one host, so no routing peer is needed — the host is just a normal enrolled peer.
- **Zitadel / external IdP** — never used; embedded Dex IdP (`AUTH_AUTHORITY=.../oauth2`, `USE_AUTH0=false`) handles auth with no extra container.
- **coturn** — superseded by the combined server's built-in STUN (`stunPorts` in `config.yaml`); no separate TURN container.

**Host peer is native, not dockerized** — the machine this stack runs on reaches its own netbird-server as a regular WireGuard peer via the native `netbird` client (systemd unit `netbird.service`, already installed — `pacman -S netbird` / AUR). Running the client itself in Docker would need `--network host` + `CAP_NET_ADMIN` + `/dev/net/tun` for zero isolation benefit over a native install, so it isn't part of this compose file. See `.setup` for re-pointing this unit at the new server.

**`edge` network** — `netbird-server` and `dashboard` join it like every other HTTP-facing stack; NPM reaches them as `netbird-server:80` / `netbird-dashboard:80`. No `ports:` entries for either beyond STUN.

**STUN port carve-out** — `3478/udp` is published directly on the host (`ports: - "3478:3478/udp"` in the compose file), unlike everything else in this stack. NAT-traversal STUN is raw UDP; NPM only proxies HTTP(S)/gRPC/websocket over TCP, so this is the same category of exception as `arr`'s gluetun utility ports (see root `CONTEXT.md`).

**gRPC through NPM** — `netbird-server` serves gRPC (signal + management) and websocket (relay) on the same port as its HTTP API. NPM's proxy host for this domain needs "HTTP/2 Support" enabled on the SSL tab plus a custom `location` block pasted into the Advanced tab (`grpc_pass` for the gRPC paths, `proxy_pass` + `Upgrade` headers for the websocket paths) — `getting-started.sh` generates this block for you as `npm-advanced-config.txt` when you choose reverse-proxy option `[3] Nginx Proxy Manager`. See `.setup`.

**Secrets** — `config.yaml` (datastore encryption key, relay auth secret, session cookie key) and `dashboard.env` are both generated by `getting-started.sh`, gitignored, never read or committed by an agent. **Not currently covered by `scripts/env/copy_env.sh`** — that script only globs `*.env` (key=value files); `config.yaml` is YAML and holds equivalent secrets, so back it up separately if you care about disaster recovery for this stack.

**Domain** — `netbird.yggdrasil.cfd`, reusing the hostname from the retired setup. Its DNS record and the dead `/etc/nginx/sites-available/netbird.conf` were removed as part of `a2b33c6`; both need restoring (DNS record) or are simply superseded (NPM proxy host replaces the old nginx conf).

**Store** — SQLite, embedded in `netbird-server`'s own data volume. No separate database container.
