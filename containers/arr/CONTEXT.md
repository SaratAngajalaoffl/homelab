# arr Stack Context

## Glossary

**arr-stack** — compose project `arr-stack` in `containers/arr/`. Torrent/media-automation apps (gluetun VPN, qbittorrent, flaresolverr, sonarr, radarr, prowlarr, homarr) behind a VPN. This is the **last** stack migrated per `docs/adr/0004-kubernetes-migration.md`'s sequencing, saved for last due to gluetun's VPN sidecar networking.

**k8s migration** — `~/homelab/helm/arr/` holds this stack's Helm chart. Unlike every other stack, this is **one multi-container Pod** (`templates/arr-pod.yaml`, hand-written — not the shared `homelab-common.deployment`, which is single-container-only): gluetun + qbittorrent + flaresolverr + sonarr + radarr + prowlarr + homarr, all as containers in the same Pod spec. Live production deployment as of 2026-09-06.

**Compose's `network_mode: "service:gluetun"` sidecar trick needed zero translation** — in Compose, qbittorrent/flaresolverr/sonarr/radarr/prowlarr/homarr each declared `network_mode: "service:gluetun"` to share gluetun's network namespace (so their traffic exits via the VPN tunnel). A k8s Pod's containers **already share one network namespace natively** — that's the whole point of a Pod — so simply putting every container in the same Pod spec reproduces this exactly, with no explicit `network_mode` setting needed anywhere.

**dockerproxy dropped, not migrated** — Compose's `dockerproxy` (`tecnativa/docker-socket-proxy`) let homarr list Docker containers via `tcp://172.17.0.1:2375` without a raw socket mount. k3s nodes run containerd, not a Docker daemon — there is no docker socket to proxy. Homarr's Docker-integration widget is simply inactive now; nothing else in this stack depended on dockerproxy.

**Config data migrated via the standard busybox-hostPath-copy pattern**, one PVC per app (`gluetun-config`, `qbittorrent-config`, `sonarr-config`, `radarr-config`, `prowlarr-config`, `homarr-config`, `homarr-appdata`) — verified exact file-count and byte-size match per pair (e.g. prowlarr: 720 files / 116021803 bytes src and dst, identical). Chart installed once first to let `local-path`'s WaitForFirstConsumer binding provision the PVCs (via a scale-to-0 + temporary migrate pod, not the real workload), copied data in, verified, then scaled the real Deployment to 1.

**The 231G `homelab-data/arr` tree stayed a hostPath mount, not a PVC copy** — same reasoning and precedent as jellyfin's `media` hostPath (see `helm/jellyfin/values.yaml`): arr's own containers (sonarr/radarr/qbittorrent) keep writing to this directory continuously, so a PVC snapshot would go stale immediately. `dataHostPath: /home/mugiwara/storage/homelab/homelab-data/arr` is mounted read-write at `/data` in sonarr/radarr/qbittorrent, identical to the original Compose mount. Single-node-only, like every other hostPath mount in this repo — revisit if a second node is ever added. jellyfin (already migrated) reads the exact same live directory at `/data/media`, so both stacks now see the same files with no copy, same as under Compose.

**Hardest networking problem across the whole migration: gluetun's VPN routing inside a k8s Pod network namespace.** Three distinct, separately-diagnosed failures had to be fixed before the tunnel actually passed traffic:

1. **`net.ipv4.conf.all.src_valid_mark=1` missing in the pod's network namespace.** Gluetun's firewall installs its actual default-route-replacement using policy routing (`ip rule` + fwmark), which the kernel silently refuses to honor without this sysctl set (reverse-path source validation on marked packets). `ip route` inside the gluetun container showed only the pod's normal `eth0` default route — no route via `tun0` — even though the WireGuard handshake succeeded and packets were reaching `tun0` (confirmed via `iptables -L -v` packet counters). Setting it via the Pod spec's own `securityContext.sysctls` failed with `SysctlForbidden` (not on this cluster's kubelet-allowed sysctl list) — and because the Deployment kept recreating the Pod on each instant failure, this briefly created ~976 `SysctlForbidden` pods before being caught and cleaned up (`kubectl delete pods --all --force --grace-period=0`, then removed the sysctl from the spec). **Fixed by setting the sysctl at the node/host level instead**: `sudo sysctl -w net.ipv4.conf.all.src_valid_mark=1` (run interactively by the user, not the agent, since it's a host-level networking change). This is currently **only set in-memory, not yet persisted** — add `net.ipv4.conf.all.src_valid_mark=1` to a file under `/etc/sysctl.d/` so it survives a reboot; not done as part of this migration.
2. **MTU too high once flannel's VXLAN overlay is added on top of WireGuard's own encapsulation.** Gluetun's auto MTU discovery picked 1400 (fine on bare Docker, wrong inside a k8s Pod sitting on a VXLAN overlay network), causing `sendmmsg: message too long` and failed data packets. Fixed via `WIREGUARD_MTU: "1320"`. Also switched `WIREGUARD_IMPLEMENTATION` from the default kernelspace to `"userspace"` while debugging point 1 (avoids relying on any kernel-level WireGuard interface quirks inside the netns) — left in place since it works and is more portable across future kubelet sysctl-policy changes, even though it wasn't the actual fix for point 1.
3. **Gluetun's own startup healthcheck raced ahead of the freshly-established tunnel and restarted it in an infinite loop**, even after points 1 and 2 were fixed — logs showed `restarting VPN because it failed to pass the healthcheck: ... lookup cloudflare.com: i/o timeout` every ~6 seconds, forever. Manually `kubectl exec`-ing into the container mid-cycle and running `nc`/`ping`/`nslookup` against the same targets **all succeeded instantly** — proving the tunnel itself worked fine, and the healthcheck's own timing/target was the problem, not connectivity. Fixed via `HEALTH_VPN_DURATION_INITIAL: "30s"` (more startup grace before the first check) and `HEALTH_TARGET_ADDRESS: "1.1.1.1:443"` (skip needing an extra DNS lookup for the health target's hostname). After this, the pod went stably `7/7 Ready` with zero restarts.

**Lesson for any future gluetun-in-k8s (or any WireGuard-in-a-pod) work**: don't trust the container's own healthcheck/restart-loop log line at face value — it can mask a working tunnel. Verify with a direct `kubectl exec` connectivity test (`nc -zv`, `ping`, `nslookup`) against the actual target before concluding the VPN itself is broken.

**Verified externally**: `sonarr.smugiwara.com` → 302 (login redirect, normal), `radarr.smugiwara.com` → 302, `prowlarr.smugiwara.com` → 302, `homarr.smugiwara.com` → 200, `qbittorrent.smugiwara.com` → 200. All new domains — Compose never had these behind NPM (see the old CONTEXT.md's ad-hoc host-port list), so there's no "preserve exact prior routing" requirement here, just following the `<app>.smugiwara.com` convention already established by jellyfin/seerr/ollama/etc.

**Secrets** — `arr-secrets` SealedSecret holds every key from `arr.env` (VPN credentials + `SECRET_ENCRYPTION_KEY` for homarr), sealed directly from the existing env file via the standard `kubectl create secret --from-env-file | kubeseal` pipeline (no multi-line values this time, unlike yggdrasil). Mounted via `envFrom` on both the `gluetun` and `homarr` containers.

**Not exposed via Ingress**: `flaresolverr` (no browser UI, only reached internally by prowlarr/sonarr/radarr over `localhost` inside the shared pod network namespace — no Service/Ingress needed at all for it).

## This was the final stack — Compose migration to k3s is now complete

Every stack listed in the old root `CLAUDE.md` "Stacks overview" table has a corresponding `helm/<stack>/` chart and live k3s deployment. Remaining follow-up work (not part of any single stack's migration, tracked separately): PVC backup CronJobs, a monitoring stack (kube-prometheus-stack + Loki/Promtail), and eventual ArgoCD adoption — all still open per the ADR's own sequencing.
