# ollama Stack Context

## Glossary

**ollama-stack** — compose project `ollama-stack` in `containers/ollama/`. Dockerized Ollama server with GPU passthrough.

**k8s migration** — `~/homelab/helm/ollama/` holds this stack's Helm chart, converted per `docs/adr/0004-kubernetes-migration.md`. One Deployment (`ollama-server`) via `helm/homelab-common`, GPU passthrough via a k8s `RuntimeClass` + the NVIDIA k8s device plugin, public endpoint via a custom Traefik `IngressRoute` (not the shared `homelab-common.ingress` helper) doing bearer-token gating. Live production deployment as of 2026-09-06; Compose stack was already stopped before this migration.

**GPU passthrough required a host-level containerd change, done by the user with sudo** — k3s bundles its own containerd, entirely separate from Docker's, so the CDI setup done for the Compose stack (`nvidia-ctk cdi generate`) doesn't carry over. The fix: register an `nvidia` runtime handler in k3s's containerd via `/var/lib/rancher/k3s/agent/etc/containerd/config.toml.tmpl`, then a k8s `RuntimeClass` named `nvidia` referencing that handler, then a pod requesting it via `runtimeClassName: nvidia` + `resources.limits: {nvidia.com/gpu: 1}`.

**A first attempt broke the cluster's networking** — running `nvidia-ctk runtime configure --config=.../config.toml.tmpl` on a *non-existent* file made it generate a **complete standalone containerd config** from vanilla defaults, rather than appending to k3s's own templated base. k3s's `.tmpl` mechanism expects `{{ template "base" . }}` at the top of the file so its own generated config (with the correct CNI plugin bin/conf dir paths for k3s's bundled flannel) gets included; nvidia-ctk had no awareness of that convention and silently dropped it. Result: the node went `NotReady` with `NetworkPluginNotReady: cni plugin not initialized` across the whole cluster (every stack, not just ollama) until fixed. **Fix**: rewrite `config.toml.tmpl` starting with `{{ template "base" . }}`, followed by the nvidia runtime section, then `sudo systemctl restart k3s`. Verified the node returned to `Ready` and all other stacks' pods recovered before continuing. **Lesson for any future host-level containerd/runtime change on this cluster: never let a generic (non-k3s-aware) config tool write `config.toml.tmpl` from scratch — always start from `{{ template "base" . }}` and only append.**

**containerd 2.x plugin path** — this k3s's bundled containerd is v2.3.4, which uses `plugins."io.containerd.cri.v1.runtime".containerd.runtimes.<name>` for custom runtime registration (containerd 2.x's CRI plugin restructuring), not the older `io.containerd.grpc.v1.cri` path from containerd 1.x. If k3s's containerd version changes significantly, re-verify this path.

**NVIDIA device plugin needed a manual node label** — `nvdp/nvidia-device-plugin`'s Helm chart ships with node affinity requiring Node Feature Discovery (NFD) labels (`feature.node.kubernetes.io/pci-10de.present`, etc.), which aren't installed on this single-node cluster. Worked around by manually labeling the node instead of installing NFD: `kubectl label node loki nvidia.com/gpu.present=true`. Revisit if NFD is ever installed for other reasons — the manual label can then be removed.

**Bearer-token auth via Traefik `IngressRoute`, not a k8s Secret** — Ollama has no auth of its own; NPM's old setup gated `infer.smugiwara.com` with a raw nginx `if ($http_authorization != "Bearer <key>")` snippet. Traefik has no built-in exact-header-match middleware, but its `IngressRoute` CRD supports `HeaderRegexp` directly in the routing rule (`helm/ollama/templates/ingress.yaml`): `Host(...) && HeaderRegexp('Authorization', '^Bearer <key>$')`. Requests without a matching header get a plain 404 (no matching router) rather than a 401 — functionally equivalent (blocked), just a different status code. **The key can't be a k8s Secret** since it has to appear as a literal string in the routing rule, which Traefik can't source from a Secret reference — instead it's passed via a gitignored `values.secret.yaml` (see `values.secret.example.yaml`), following the pre-Sealed-Secrets convention for values that genuinely can't be expressed as a real k8s Secret: `helm upgrade --install ollama . -f values.secret.yaml`. TLS is requested via a standalone cert-manager `Certificate` resource (IngressRoute doesn't get the `cert-manager.io/cluster-issuer` annotation shim a plain Ingress does).

**Reused the existing key** — the same `infer.smugiwara.com` bearer token from NPM's config was carried over (provided directly by the user, sealed into `values.secret.yaml`, never displayed in chat) rather than rotated, so no existing API clients needed updating.

**Fresh-install trap did NOT apply here** — unlike nextcloud/netbird, Ollama's data dir starts genuinely empty (`total blobs: 0`) with no auto-seeded content, so there was no need to catch/undo an auto-init before copying real data in — the copy-then-restart sequence was still followed (scale to 0, busybox migrate pod, wipe, stream, verify, scale to 1) purely to avoid the earlier "Ready but running fresh/empty" risk, and to avoid two processes writing `/root/.ollama` concurrently.

**Data migration (verified)** — 23GB, 20 files (`models/blobs/`, `models/manifests/`, `id_ed25519` keypair, `cache/`). 19/20 files matched exactly; the one difference, `cache/model-recommendations.json`, is a disposable server-regenerated cache file (confirmed via server logs: `"model recommendations cache sleep scheduled"`), not real data loss — same category as jellyfin's WAL files and nextcloud's live artifacts. md5sum verified on the 23GB model blob, a manifest file, and the SSH keypair. Post-restart: `ollama list` shows both models (`qwen3.6:35b`/`latest`, `glm-5.2:cloud`); a real inference call through the public endpoint returned `done_reason: stop` (not truncated, confirming `OLLAMA_CONTEXT_LENGTH=32768` carried over) with `ollama ps` showing the GPU actively loaded (64%/36% CPU/GPU split, same partial-offload pattern as the original host install).

**`webui`'s `OLLAMA_BASE_URL`** will need to point at this new in-cluster service (`ollama-server.homelab-ollama.svc.cluster.local:11434` or similar) once `webui` itself migrates — not yet done, since `webui` is still on Compose reaching the old `ollama:11434` container name.
