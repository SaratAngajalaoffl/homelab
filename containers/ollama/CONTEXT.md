# ollama Stack Context

## Glossary

**ollama-stack** — compose project `ollama-stack` in `containers/ollama/`. Dockerized [Ollama](https://ollama.com) server, replacing the host's native `ollama.service` systemd unit. Runs local models on the RTX 4070 and exposes them both internally (to `webui` and any other edge-network container) and publicly (via `nginx-proxy-manager`, key-gated).

**GPU passthrough via CDI, not `deploy.reservations.devices`** — this host's Docker (29.x) resolves the classic `--gpus all` / `deploy.resources.reservations.devices: [{driver: nvidia, ...}]` forms through a multi-vendor CDI probe that errors `AMD CDI spec not found` even though only an nvidia CDI spec exists (this desktop also has an AMD iGPU). The fix that actually works is the explicit CDI device string `devices: ["nvidia.com/gpu=all"]` in the compose file. Prerequisite on the host (not in this repo, see `.setup`): `nvidia-container-toolkit` installed and `sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml` run once — no `/etc/docker/daemon.json` edit or `docker` restart needed, so this didn't bounce any other stack.

**No auth of its own** — Ollama's HTTP API has zero built-in authentication. Internally that's fine (every edge-network container already trusts every other one by container name — same model as `atuin_server`, `immich_server`, etc.). Publicly it's not, so the NPM proxy host for `infer.smugiwara.com` carries a custom Advanced-tab nginx snippet that 401s any request without a matching `Authorization: Bearer <key>` header before it reaches the container. The key lives only in NPM's own config/DB (`homelab-conf/nginx-proxy-manager/data`, gitignored runtime state) — there's no `ollama.env` in this repo, because the stack itself holds no secret. See `.setup` for the exact snippet and how to rotate the key.

**`edge` network only** — no stack-internal network, no `ports:`. `webui` (and anything else on `edge`) reaches it directly at `ollama:11434`, unauthenticated, same as every other internal cross-stack call in this repo. Only the public path goes through NPM's key check.

**`OLLAMA_CONTEXT_LENGTH=32768` is a deliberate override, not a default.** Ollama auto-sizes context from available VRAM, and picked a conservative 4096 by default for `qwen3.6:35b` (23GB Q4 on a 12GB GPU, already partially CPU-offloaded). That's too small for this model's own reasoning — it burns thousands of tokens "thinking" before the final answer — so at 4096 the prompt + thinking exhausted the window before any final content came out: webui showed a "Thought for Ns" block with an empty response after it, and `docker logs ollama` showed `truncating input prompt`. Confirmed by explicitly bumping the context and re-testing (`done_reason` went from truncated to `stop`, with real content after the thinking block). Costs more CPU-side RAM for KV cache, not VRAM. If other models loaded here have similarly verbose reasoning and still truncate at 32768, raise it further; if you load smaller/non-reasoning models and want faster loads, this is a shared server-wide setting, not per-model — a future per-model override would need Ollama's per-request `options.num_ctx` instead (settable from webui's model Advanced Params) rather than this env var.

**Data** — `homelab-conf/ollama/data` → `/root/.ollama` (models, blobs, manifests). Seeded once from the host's native install (`/usr/share/ollama/.ollama`, root-only 700) via a one-time `sudo rsync` — see `.setup` — rather than re-pulling the existing ~23GB `qwen3.6:35b` model over the network. New models pulled after cutover (`docker exec ollama ollama pull ...`) land here going forward, not on the host path.

**Host cutover** — the native `ollama.service` systemd unit is disabled once the container is verified serving on the GPU (`.setup` step 5), so the two don't fight over VRAM or port 11434. `webui`'s `OLLAMA_BASE_URL` was repointed from `http://host.docker.internal:11434` to `http://ollama:11434` as part of this migration (`containers/webui/docker-compose.yml`).
