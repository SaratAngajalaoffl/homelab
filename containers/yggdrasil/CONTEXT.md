# yggdrasil Stack Context

## Glossary

**yggdrasil-stack** — compose project `yggdrasil-stack` in `containers/yggdrasil/`. Self-hosted deploy of `yggdrasil-hq/yggdrasil-core` control-plane (landing, web, docusaurus, api, orchestrator, postgres, minio).

**k8s migration** — `~/homelab/helm/yggdrasil/` holds this stack's Helm chart, converted per `docs/adr/0004-kubernetes-migration.md`. Seven components via `helm/homelab-common`: five Deployments (`landing`, `web`, `docusaurus`, `api`, `orchestrator`), one StatefulSet (`db`, Postgres), one Deployment+PVC (`minio`). Four Ingresses (`yggdrasil.cfd` → landing, `app.yggdrasil.cfd` → web, `api.yggdrasil.cfd` → api, `docs.yggdrasil.cfd` → docusaurus) — domains kept on `yggdrasil.cfd`, not migrated to `smugiwara.com` like every other stack, matching the existing repo convention (this is the app's own name). Live production deployment as of 2026-09-06; Compose stack was already stopped before this migration.

**In-cluster service names replace Compose container names in one secret value** — `DATABASE_URL` (`postgresql://yggdrasil:***@postgres:5432/yggdrasil` in Compose) had its host rewritten from `postgres` to the in-cluster Service name `yggdrasil-db` via a `sed` pass on a temp copy of `yggdrasil.env` before sealing — password/user/db untouched, never displayed. `S3_ENDPOINT`, `API_INTERNAL_URL`, `ORCHESTRATOR_URL` didn't need this treatment since they were already plain (non-secret) `environment:` values in the compose file, updated directly in `values.yaml` to `http://yggdrasil-minio:9000` / `http://yggdrasil-api:3000` / `http://yggdrasil-orchestrator:8080`.

**Multi-line secret value required a custom parser** — `yggdrasil.env`'s `GITHUB_APP_PRIVATE_KEY` is a quoted, multi-line PEM RSA key. `kubectl create secret generic --from-env-file` cannot parse multi-line values at all (it errored treating each continuation line as an invalid new key). Worked around with a small one-off Python script (`parse_env_to_secret.py`, not checked into the repo — scratch tooling) that properly handles quoted multi-line `KEY="..."` blocks and emits a plain Secret manifest piped straight into `kubeseal`, so the private key was never displayed or written to a plaintext k8s Secret. All 29 keys from `yggdrasil.env` verified present in the resulting `SealedSecret` (checked by key name only, not value).

**Postgres data migrated via `pg_dump`/restore, not a raw file copy** — unlike some other stacks, this used the established Postgres pattern (atuin/immich precedent): the *stopped* Compose Postgres data directory was booted in a **temporary plain `docker run` container** (same `postgres:16-alpine` image, host data dir mounted, no compose/k8s involved) just long enough to `pg_dump --no-owner --no-acl --clean --if-exists`, then the container was removed. The dump was piped into the fresh k8s `yggdrasil-db-0` pod via `psql`. Verified via matching row counts on `organizations` (1), `jobs` (0), `features` (0) — this is a very early-stage/low-data instance, so row counts are small but exact.

**MinIO data migration (verified)** — 31/32 files; the one "extra" file on the destination (`.minio.sys/tmp/<uuid>`) was confirmed to be a MinIO-internal temp/lock artifact created during the brief window between the fresh pod's first boot and the wipe-and-restore, not real data — verified via full path diff, not just count.

**Verified externally**: `yggdrasil.cfd` (landing) → 200, `docs.yggdrasil.cfd` → 200, `app.yggdrasil.cfd` → 307 redirect to `/projects` (normal Next.js auth-gate behavior, not an error), `api.yggdrasil.cfd` → 404 body `Cannot GET /` (Express's standard response for an unhandled root route — the API itself is up and listening per its own logs, `API listening on :3000`; this isn't a failure, just no `/` handler).

**k3s cluster targeting still configured entirely in-app, unchanged by this migration** — per the pre-existing architecture (see the original CONTEXT.md note this file replaces), the Orchestrator's *target* Kubernetes cluster (where it schedules actual project/agent-job work) is configured through the yggdrasil web UI itself, not by this Helm chart or any file in this repo. **Worth deciding deliberately, not by default, whether that target cluster should be this same homelab k3s cluster** (self-hosting yggdrasil's own job workloads alongside every other homelab stack) or a separate cluster — this wasn't addressed as part of the migration and is an open decision for whenever project/agent job execution is actually turned on.

**Still not wired up (unchanged from Compose)**: GitHub App private key is present (repo access should work), but reaching a deployed project (`<project-slug>.apps.${APPS_BASE_DOMAIN}`) from outside the host is still not wired to any ingress — same open item as before migration, now inherited by k8s. Agent-images (`SPEC_GRILL_IMAGE`/`FEATURE_BUILD_IMAGE`/`TEST_RUN_IMAGE`/`DESIGN_GRILL_IMAGE`) were carried over as whatever `yggdrasil.env` already had (not verified further, out of scope for infra migration).
